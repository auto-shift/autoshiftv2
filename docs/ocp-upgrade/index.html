OpenShift fleet upgrades¶

AutoShift upgrades OpenShift Container Platform on Day 2 the same way it configures everything else: labels in values files, policies from GitOps, and clusterset membership as the blast-radius control. There is no separate upgrade orchestrator. A cluster upgrades when it is opted in and its clusterset's openshift-version is higher than the version the cluster is already running.

Note

Topology Aware Lifecycle Manager is not used here. It needs literal upgrade coordinates in the root policy and cannot consume AutoShift hub-template labels. Red Hat Advanced Cluster Management for Kubernetes also has no progressive policy rollout hook for Policy objects. Membership in a clusterset is the staging lever that fits this model.

What happens on one cluster¶

When autoshift.io/openshift-upgrade: 'true' is set, four policies run in order. All share one placement. The Cluster Version Operator (CVO) still performs the upgrade; the policies only set the channel, validate the target, write desiredUpdate, and report completion.

flowchart LR
  A["1. Channel<br/>enforce"] --> B["2. Allowed<br/>inform"]
  B --> C["3. Upgrade<br/>enforce"]
  C --> D["4. Status<br/>inform"]
Step Policy Mode What it does
1 policy-openshift-upgrade-channel enforce Sets ClusterVersion.spec.channel so status.availableUpdates recomputes for the desired channel. Without this, a y-stream target can deadlock the next check.
2 policy-openshift-upgrade-allowed inform Confirms the target is safe to apply. Compliant when the target is already running, appears in status.availableUpdates with a release image, or is already accepted (status.desired.version or a Partial history entry). NonCompliant on a plain miss (wrong or unpublished version). A Recommended: False entry under status.conditionalUpdates is handled by a sibling check; see Conditional updates. Step 3 depends on this policy.
3 policy-openshift-upgrade enforce Writes spec.upstream from config.openshift-upgrade.upgradeGraphUrl and, when not already Progressing, spec.desiredUpdate.version plus spec.desiredUpdate.image. The image is copied from status.availableUpdates (or from status.conditionalUpdates when conditional upgrades are allowed). The CVO then upgrades the cluster.
4 policy-openshift-upgrade-status inform Compliant only after the latest Completed history entry is at or above the target. This is the wave-done gate. Do not use step 3 for that: it goes Compliant as soon as desiredUpdate is written, long before the CVO finishes.

Guards built into the enforce policy:

  • Semver. desiredUpdate is written only when target > current. Clusters already at or above the target are a Compliant no-op. Downgrades are never attempted.
  • In flight. While Progressing is True, the policy does not rewrite desiredUpdate, so it does not fight an upgrade that has already started.
  • Dependencies. Step 3 stays Pending until steps 1 and 2 are Compliant.

Note

Completion is decided in template logic, not by matching status.history as a list field. Red Hat Advanced Cluster Management does not reliably match status lists, so the status policy forces NonCompliant with a mustnothave on the ClusterVersion until the target is reached. Upgrade failure visibility still comes from OpenShift upgrade alerts, not from these policies.

Labels¶

Set these on the target clusterset (or override one cluster). Prefix in values files is bare; the cluster-labels policy stamps autoshift.io/ at runtime.

Label Purpose Example
openshift-upgrade Opt the cluster in to Day 2 upgrades 'true'
openshift-version Target OpenShift version. Shared with operator-catalog tooling. Upgrade runs only when this is greater than the running version. '4.22.8'
openshift-upgrade-channel ClusterVersion channel 'stable-4.22'
openshift-upgrade-allow-conditional Allow a Recommended: False target from status.conditionalUpdates 'false'

Example clusterset fragment:

hubClusterSets:
  managed-upgrade:
    labels:
      openshift-upgrade: 'true'
      openshift-version: '4.22.8'
      openshift-upgrade-channel: 'stable-4.22'
      openshift-upgrade-allow-conditional: 'false'

Config¶

The OpenShift Update Service graph URL is config, not a label. The enforce policy reads config.openshift-upgrade.upgradeGraphUrl from the cluster's rendered-config ConfigMap and writes it to ClusterVersion.spec.upstream. See config-and-labels.md. You do not need to set this key if the cluster can reach the public graph.

Key Purpose Default
config.openshift-upgrade.upgradeGraphUrl OpenShift Update Service graph. Point this at a local service when the cluster is disconnected. https://api.openshift.com/api/upgrades_info/v1/graph 
hubClusterSets:
  managed-upgrade:
    config:
      openshift-upgrade:
        upgradeGraphUrl: 'https://api.openshift.com/api/upgrades_info/v1/graph'

Roll out a new version to a cluster¶

There are two supported patterns. Use the simple path when one clusterset already owns the cluster and you only need to bump OpenShift. Use waves when you must stage a fleet (or a new AutoShift release together with a new OpenShift version).

Simple path: bump the target on the owning clusterset¶

  1. Confirm the cluster is healthy and that the target appears (or will appear after the channel change) in the update graph for that channel.
  2. In the clusterset values file that already owns the cluster, set:
labels:
  openshift-upgrade: 'true'
  openshift-version: '4.22.8'          # new target, must be > current
  openshift-upgrade-channel: 'stable-4.22'
  1. Commit and push. OpenShift GitOps syncs; Red Hat Advanced Cluster Management places the policies.
  2. Watch the sequence on that cluster (see Watch progress):
  3. channel Compliant
  4. allowed Compliant (or conditional NonCompliant: read the risk before overriding)
  5. upgrade Compliant (desiredUpdate written)
  6. status Compliant (cluster actually at target)
  7. Leave openshift-upgrade: 'true' if future bumps on the same clusterset should auto-apply, or set it back to 'false' if upgrades should be opt-in per bump.

Important

Never flip openshift-upgrade: 'true' on a clusterset that already holds many clusters at an older version unless you intend every member to upgrade together. Red Hat Advanced Cluster Management fans the policy out with no per-cluster staging inside one placement.

Fleet path: empty upgrade clusterset and move clusters in waves¶

Blast radius is membership. Create (or reuse) a clusterset whose labels already describe the new OpenShift target, keep it empty or canary-only, then move clusters into it one wave at a time.

  1. Prepare the destination clusterset with the new OpenShift labels (openshift-upgrade: 'true', new openshift-version, matching channel). Prefer a versioned AutoShift release so the destination is empty until you move members. See gradual-rollout.md.
  2. Move a canary into that clusterset. Prefer a git change to config.clusterSet / config.versionTag in autoshift/values/clusters/<name>.yaml so cluster-set-assignment stamps membership. Do not rely on a durable oc label override if assignment owns the cluster.
  3. Wait for the canary until policy-openshift-upgrade-status is Compliant (and the GitOps Application for the upgrade policies is Healthy).
  4. Move the next wave, verify, repeat until the fleet is on the new version.
  5. Rollback a membership move with git revert of the assignment commit. That returns the cluster to the previous clusterset; it does not roll OpenShift backward.
flowchart TB
  Prep["1. Destination clusterset<br/>openshift-upgrade true<br/>new openshift-version"]
  Canary["2. Move canary into destination"]
  Verify["3. Wait for status Compliant"]
  Wave["4. Move next wave"]
  Done["5. Fleet at target"]

  Prep --> Canary --> Verify --> Wave
  Wave --> Verify
  Verify --> Done

A wave is a commit that changes membership for N clusters. OpenShift GitOps reconciles it. The completion gate tells you when the next commit is safe. Nothing auto-proceeds to the next wave; that gate is your commit cadence or a thin script that reads compliance.

Conditional updates (Recommended: False)¶

Sometimes the CVO lists the target under status.conditionalUpdates instead of status.availableUpdates, with Recommended: False. That means a known risk matched this cluster. The inform policy openshift-upgrade-allowed-conditional fails with the CVO reason and risk text, and Governance shows that message. The enforce policy does not start.

To accept that risk after review and a canary:

labels:
  openshift-upgrade-allow-conditional: 'true'

Effects:

  • The conditional inform gate stops failing.
  • The plain allowed gate treats the conditional release image as found.
  • The enforce policy copies desiredUpdate.image from status.conditionalUpdates.

Leave the label at 'false' (or unset) unless that override is intentional. Do not set 'true' on a populated clusterset before a canary has completed the same target.

Watch progress¶

Prefer the status policy, not the enforce policy:

oc get policy -n policies-autoshift policy-openshift-upgrade-status \
  -o jsonpath='{range .status.status[*]}{.clustername}{"\t"}{.compliant}{"\n"}{end}'

See every stage for the upgrade set:

oc get policy -n policies-autoshift \
  -o custom-columns=NAME:.metadata.name,COMPLIANT:.status.compliant \
  | grep openshift-upgrade

OpenShift GitOps ships a health check for Policy. The Application that deploys these policies is Healthy only when every policy in the set is Compliant. Because the status policy is included, that means the upgrade finished. Expect the Application to sit Degraded for the duration of an upgrade; that is the gate working.

Hub-of-hubs¶

Each Red Hat Advanced Cluster Management layer only sees its own clusters. Roll top-down (hub-of-hubs, then spoke hubs, then leaf spokes) so each hub runs a version that supports the clusters it manages. Apply the upgrade labels on the right clusterset at each layer and run waves in that order. See hub-of-hubs.md.
